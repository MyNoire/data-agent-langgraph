# SQL 评测

衡量的是"给一个问题，最后执行出来的结果对不对"。实现在 `src/querypilot/evaluation/sql/`，入口是 `querypilot eval direct` 和 `querypilot eval graph`。

## 题集

题目来自 [BIRD Mini-Dev](https://github.com/bird-bench/mini_dev)（SQLite 版）：

- **12 题开发集**：日常调试用，`evals/bird_smoke_manifest.json`；
- **冻结的 100 题**：最终验证用，`evals/bird_final100_manifest.json`。
- **两库 88 题**：toxicology（40 题）和 student_club（48 题）在 Mini-Dev 里的全部题，`evals/bird_toxicology_student_club_manifest.json`。知识库目前只有这两个库，所以检索接入查询图之后的对比（R5）都在这份题集上做；题号与[检索评测](retrieval-evaluation.md)的 88 题相同。其中 16 道属于冻结集，每题带 `frozen` 标记，评测的逐题记录里原样带上：冻结题一起计分，失败分析只看其余 72 道。

仓库里只提交 manifest，记录题号、来源 URL 和各文件的 sha256；原题和数据库放在 Git 忽略的 `data/` 下，用 `querypilot data bird ...` 命令准备。两库题集用 `querypilot data bird select-databases --database-id toxicology --database-id student_club --output evals/bird_toxicology_student_club.json` 生成：来源文件的 sha256 必须和冻结 manifest 记录的一致，题集文件留在本地，旁边的 manifest 提交。冻结题的使用规则见 [ADR 0001](../adr/0001-frozen-set-for-component-eval.md)。

## 两种跑法

| 命令 | 链路 | 说明 |
|---|---|---|
| `eval direct --provider model` | 问题加完整 Schema，直接让模型生成 SQL | 模型基线 |
| `eval direct --provider fixture` | 把金标准 SQL 当作预测 | **只用来验证评测管线**，分数不能当成模型能力 |
| `eval graph` | 走 LangGraph 四节点查询图：读结构 → 生成 → 安全检查 → 只读执行 | 和线上查询同一条链路 |

`eval graph --workers N` 同时跑 N 道题（默认 1）：工作线程里只跑查询图和金标准 SQL，结果比对、逐题记录和进度事件都在主线程，报告仍按题集顺序。单题出错照常记为 error 并继续；主线程出错或被 Ctrl+C 中断后不再开始新题。图评测每题的耗时从这道题开始跑图量到金标准 SQL 执行完，不含排队和结果比对；`workers` 大于 1 时会被同时进行的请求拉高，**耗时只在线程数相同的运行之间比较**；线程数记在运行配置和报告里。

`eval graph --context-source` 选模型收到的 Schema 从哪里来（Context Source，编译图时选定，见 [GLOSSARY](../../GLOSSARY.md)）：`schema`（默认）是每张表的表名和列名；`ddl` 是这个库全部用户表的 CREATE TABLE 原文，按表名排序、空一行分隔，从 SQLite 的 `sqlite_master` 现场读取。`knowledge` 是这个库在知识库里的全部知识，经组装和渲染（当前规则版本 `r5-schema-v3`：表有数据约定时接在记录粒度后，命中的列有取值样例时接在说明后，没被命中的列仍然只在字段目录或建表语句里。没有这两行的旧 Corpus 渲染结果与 `r5-schema-v2` 逐字相同；R5 的运行用的是 `r5-schema-v1`，它和 v2 只在缺关联语义或有复合外键的关系上不同，R5 两个库的渲染逐字相同）后交给模型，`--structure-format columns`（默认）把表结构写成字段目录、主键、外键三行，`ddl` 换成建表语句原文；它需要 `--retrieval-cases <检索题集>`，从中取各库的 Knowledge Scope，题集用到的库缺 Scope 时在开始前报错。`retrieval` 用问题原文在这个库的 Scope 里检索一次（`--method` 默认 `hybrid`，`--rerank / --no-rerank` 默认重排，`top_k` 固定为 10），只把命中的表（加上它们的表 Chunk）渲染给模型，结构写法和 `--retrieval-cases` 与 `knowledge` 相同；没有命中或检索失败的题记为 error，`error_type` 是检索错误的类别（如 `no_match`、`embedding_error`），然后继续下一题。`retrieval` 的每道题另记 `tables_complete`：这道题 Relevant Set 的表（取自 `--retrieval-cases`，按题号对应，缺题号时在开始前报错）是否都出现在 Hit 所属的表里，检索失败的题记为没拿全；报告的 `tables_complete` 按"拿全 / 没拿全"分别给出题数、执行匹配数和比例，整体和分库各一份。用来分清 SQL 写错是检索没给全，还是给全了模型仍然写错。vector、hybrid 和重排会调用付费服务。所有来源下安全检查允许的都是这个库的全部用户表。Context Source 记在运行配置和报告里，`knowledge` 和 `retrieval` 另记结构写法、渲染版本和各库的 Scope，`retrieval` 再记 `method`、`rerank`、`top_k` 和实际用到的检索版本；建表语句、知识正文和 Hit 本身不写进日志和运行记录。

`--small-to-big`（默认关闭）只用于 `retrieval` 来源：照常检索一次，进入上下文的表不变，但每张被命中的表以完整的 Document 交给模型（表块、全部列的说明和取值、这张表出向的全部关系），内容从这个库的 Scope 全量读出，渲染与 `knowledge` 来源里这张表逐字相同，表的先后仍按检索名次（见 GLOSSARY 的 Small-to-Big）。渲染版本不变；`tables_complete` 照常按 Hit 所属的表计算，与开关无关。开关写进运行配置、报告和 `export-public`（retrieval 来源总是记下 `small_to_big`，其他来源不记）；在其他来源上使用时，开始前报错，不留运行记录。

`--evidence-mode oracle` 会把 BIRD 的人工提示（evidence）交给模型。这是隔离实验，不代表系统真实的能力，默认为 `none`。

## 计分

每道题有两个口径的结果（定义见 [GLOSSARY](../../GLOSSARY.md)，主指标的取舍见 [ADR 0003](../adr/0003-content-match-as-primary-sql-metric.md)）：

- **严格执行匹配**（`execution_match`）：预测 SQL 和金标准的执行结果逐行相同，忽略行的顺序，保留重复行。
- **内容匹配**（`content_match`）：预测结果包含了金标准结果的全部内容，只在形式上不同。只承认四种形式差异：预测可以多出列、列的顺序可以不同；重复行不计（按行的集合比较）；文本去掉首尾空白和末尾一个 `%` 后是十进制数字的，按这个数值比较（`'44.315%'`、`'44.315'`、`44.315` 相同，`4` 与 `4.0` 相同）；预测的一个文本列等于金标准几列用单个空格拼接的值（`'Sacha Harrison'` 对 `'Sacha'`、`'Harrison'`），算覆盖了这几列。数值要四舍五入才相等、比例和百分比要换算才相等、行的集合不同（多一行、少一行、行数或形状不同）都不算。严格执行匹配的题一定内容匹配。

SQL 评测的结论以内容匹配为主，两个口径总是并列报告。

按严格口径，每道题只会落进一类：

- **matched**：严格执行匹配。
- **mismatched**：能执行，但结果不严格一致（其中可能有内容匹配的题）。
- **error**：没有生成预测、被安全检查拒绝，或者执行报错；这类题两个口径都记为不匹配。

`failure = mismatched + error`。另外单独统计 `valid_sql`（能通过检查并执行的 SQL 数）、`no_prediction` 和 `content_match`（内容匹配的题数），它们不能和上面三类直接相加。报告的 `execution_accuracy` 是严格执行匹配率，`content_match_rate` 是内容匹配率；如果所有题都没有预测，两者都记为空（`null`），不记成 0%。`retrieval` 来源的 `tables_complete` 拆分同样给出两个口径（`matched` / `rate` 与 `content_matched` / `content_rate`）。

**两个口径都受行数上限影响，都不等于官方 BIRD EX。** 比较不同实验时必须固定行数上限、超时和字节上限。2026-11-19 加入内容匹配之前的运行记录里只有严格口径（R5 的运行已离线重算，见下文）。

## 报告与可追溯

- 报告记录题集 sha256、模型、提示词版本（`direct-v2`）、图版本（`single-v2`，`schema` 来源的行为与 `single-v1` 相同）、Context Source、evidence 模式、执行上限、逐题结果，以及 P50/P95 耗时。
- **token 用量**取自模型接口的返回，不另外用 tokenizer 估算：逐题记录里的 `prompt_tokens`（提示词）和 `completion_tokens`（模型输出，推理模型的推理 token 也算在内），报告的 `token_usage` 给出两项各自的题数、总数、平均数和中位数。只对有值的题统计：fixture 不调用模型，没有用量；接口没返回用量的题记为空。
- 详细结果包含问题和预测 SQL，放在运行目录的 `private/` 下。`eval export-public` 按字段白名单导出一份可以分享的副本（包括线程数、Context Source、token 用量、两个口径的匹配结果和每题的冻结标记），但里面仍然有 `predicted_sql`，分享前要检查。
- 对比实验要固定题目、数据库快照、模型、提示词、检索配置和评测器，并保存逐题结果。只靠 12 题，不能支撑准确率结论。

结论（±2 道题以内当作噪声，逐题只看 72 道非冻结题）：

- **检索到的知识能不能帮模型写对 SQL？** 和不给知识（①）相比没有量得出的提升：六组在非冻结题上都在 35–37 道之间。但检索也没有变差：⑤⑥ 和全量知识（③④）持平，输入只有全量知识的约 37%（平均 712 对 1910 token）。逐题看，全量知识答对、检索答错的非冻结题只有 2–3 道（⑤ 2 道、⑥ 3 道，其中 1411 是表没拿全），反方向也有 1–3 道。
- **知识内容有没有用？** 这一轮量不出来：③④ 与 ①② 的差在噪声内。72 道非冻结题里有 29 道六组都错，给模型更多结构和知识帮不上这些题。
- **建表语句是不是关键？** 不是：四对"ddl 写法 − columns 写法"的差是 +1、+2、−1、+3（非冻结 −1、+2、−1、+2），都在噪声内。
- **表没拿全的题大多做错**：hybrid + 重排有 9 道题缺表，只对了 1 道；拿全的 79 道对了 54%。这 9 道都在 student_club。拿全率与检索评测的 Complete Recall@10 一致（hybrid + 重排 89.8%，lexical 84.1%）。缺表的题也可能本身更难，这里只说明相关，不说明因果。
- **代价**：hybrid + 重排让每题 p50 从全量知识的约 6.5 秒升到 10–11 秒（多了 Embedding 和重排两次服务调用）；lexical 的 p50 约 5.5 秒，比全量知识还快。
- **前提**：toxicology 只有 20 个 Chunk，`top_k=10` 已经是一半，所以 toxicology 的表在 hybrid + 重排下全部拿全；每组只跑一次，同一配置重跑的波动没有测过。

八次运行的模型费用合计约 0.77 元（按用户给的价格，检索组每次约 0.08 元），另有硅基流动的 Embedding 和重排各 176 次调用。这一轮没有根据结果调整 `top_k`、渲染规则、检索配置或提示词。
