# 管理面与服务面分离，在用语料由仓库里的配置指定

状态：已接受（2026-11-22），待实现（`.scratch/serving-boundary-and-retrieval-tool/spec.md`）。

知识准备、校验和评测属于**知识管理员**；**业务用户**的查询 Agent 只能经检索 tool 只读地使用知识。两者在三层上分开：

- **能力**：Agent 只拿到检索 tool，模型只提供查询文本；Knowledge Scope、检索方法和 top_k 由系统决定。登记数据库是管理操作，只在管理员 CLI 提供，不在 HTTP 上提供。
- **代码**：检索、查询和用户入口只能导入 knowledge 里读取相关的名字，由架构测试守住。
- **凭据**：用户端使用只含 reader DSN 的配置类型，部署时只下发 reader DSN。

用户端检索哪份 Corpus 由 **Active Corpus（在用语料）** 决定：仓库里一份由知识管理员维护的配置。用户端启动时读取，并核对业务库当前的 Schema Version，不一致就停用这个库。评测自己指定 Knowledge Scope，不读这份配置。

## Considered Options

- **只靠数据库角色**：不用改代码，但用户端代码仍能一步调到构建和导入，进程也可能持有写凭据。
- **把 knowledge 拆成两个包**：隔离更清楚，但改动大；按名字检查导入已能挡住同样的误用。
- **发现 admin DSN 就拒绝启动**：开发机三个 DSN 共用一个 `.env`，会直接起不来。
- **在用语料存进 PostgreSQL**：可以热切换，但要加迁移和管理命令；目前单实例，配置文件加 Git 历史已经够用。
- **沿用评测题集里的 Scope**：评测资料会决定线上知识，职责颠倒。

## Consequences

- 切换在用语料要改配置、提交并重启用户端。
- 启动检查发现不了运行中的改表，也发现不了只改数据造成的取值样例过期。
- 读配置类型不是进程级隔离：同一台机器上能读到完整 `.env` 的进程仍能拿到写凭据，所以部署时的凭据下发仍然必要。
- 将来辅助开发者建库的 Agent 属于管理面：只起草，批准由人完成，不与查询 Agent 共享工具和凭据。
- 这不是访问授权：业务用户能访问哪些库、哪些列，由以后的 Access Grant 决定。
