# 内容匹配与取值样例

Status: ready-for-agent

## 问题

R5 的六组 Context Source 在两库 88 题上的执行匹配都在 42–46 之间，非冻结题 35–37/72，彼此差距都在噪声内。用户（项目开发者，也是学习者）从失败分析里看到两件事：

- **口径掩盖了真正的错误。** 72 道非冻结题里有 29 道六组都错，其中一半以上其实拿到了正确的数据，只是形式不同：多选了列、有重复行、姓名拼成一列、数字写成带 `%` 的字符串。严格执行匹配把它们和真正答错的题算成一类。QueryPilot 的结果是给用户和 Agent 里的大模型看的，形式无所谓，内容必须对。
- **知识里缺"数据长什么样"。** 剩下真的答错的题里，表和列都拿到了，缺的是列里实际存的值（`'Meeting'` 而不是 `'meeting'`，`income.source` 里有 `'Fundraising'`）和表的存储约定（`connected` 每条连接正反各存一行）。现在的知识来自 BIRD 字段说明，对这些覆盖很少，有时还会误导（`event.type` 的说明举例全是小写）。

所以"知识内容有没有用"这个问题在 R5 量不出来：一来口径太严，二来知识里恰好缺了最有用的那部分。

## 解决方案

先改口径，再改知识：

1. **内容匹配（Content Match）**：新增一个 SQL 评测指标，作为结论的主指标（[ADR 0003](../../docs/adr/0003-content-match-as-primary-sql-metric.md)）。它只承认四种形式差异：多出列或列顺序不同、重复行、数字写成字符串、几列用空格拼成一列。现有的指标改称**严格执行匹配**，计算方式不变，两者始终并列。R5 的八次运行离线重算一遍。
2. **取值样例（Value Samples）**：从业务库只读取出每列的真实取值，写进列 Chunk。取值少的文本列给出全部取值，其余列给几个样例展示格式，隐私列不给。
3. **数据约定（Data Convention）**：对两个库的所有表统一查一遍数据，把观察到的存储性质写进语义配置，标为观察所得，用户审阅批准后写进表 Chunk。
4. 用新的输入构建两份新 Corpus（toxicology、student_club 各一份），导入同一个知识库，旧 Corpus 不动；重跑检索评测和 SQL 评测的 ③⑤ 两组，用两个口径回答"知识内容现在有没有用"。

## 实现决定

### 内容匹配

- 评测模块新增一个纯函数：输入预测结果行和金标准结果行（都是执行器返回的、受行数上限截断后的行），返回是否内容匹配。从评测模块的公开入口导出，评测运行和离线重算都用它。
- 规则：
  - **值的比较**：数字按数值比较（`4` 等于 `4.0`）；文本去掉首尾空白和末尾一个 `%` 后能解析成数字的，按这个数字参与比较；数值必须完全相等，不做取整和比例换算。其他值原样比较，`NULL` 只等于 `NULL`。
  - **列的覆盖**：金标准的每一列要被预测结果覆盖。覆盖的方式有两种：预测结果的某一列和它对应；或者预测结果的某个文本列，逐行等于金标准里几列的值用单个空格拼接起来。预测结果的每一列最多用一次，多出来的列不管。
  - **行的比较**：按选定的列映射取出预测结果的投影，与金标准都按行的集合（去重）比较，相等即匹配；存在任何一种映射使之相等就算匹配。
  - 金标准为空时，预测也为空才算匹配；预测为空、金标准不为空则不匹配。
  - 严格执行匹配为真时，内容匹配一定为真（在测试里体现）。
- 映射的搜索直接枚举。金标准的列数很少，不做剪枝，也不设上限，等出现慢的情况再说。
- 现有的 `outcome`（matched / mismatched / error）和 `execution_match` 保持严格口径的含义不变。逐题记录新增 `content_match`；没有预测或执行出错的题记为 `false`。
- 报告汇总在现有执行匹配的位置并列给出内容匹配的题数和比例，`tables_complete` 的拆分也一样。`export-public` 的白名单加上 `content_match` 和对应的汇总字段。
- R5 八次运行的离线重算用一个提交进仓库的一次性脚本完成：读取各运行保存的预测 SQL，用只读连接重新执行预测 SQL 和金标准 SQL，套用同一个函数，输出逐组的两个口径。结果写进 SQL 评测文档并标明"离线重算"。不新增 CLI 命令，也不改写已有的运行目录。

### 取值样例

- 知识准备新增一步：只读打开业务 SQLite，按 Catalog 的列逐列取值，生成一份取值样例文件，作为构建 Corpus 的新输入。这一步需要语义配置里的隐私名单，隐私列在这一步就跳过，所以它们的值不会落盘。
- 取值规则（`value-samples-v1`）：
  - 声明类型是 TEXT、去重后非空取值不超过 20 个、又不是主键或外键列的：全部取值按值排序列出。
  - 其他列：取出现次数最多的 3 个非空值，次数相同时按值排序。
  - 每个值超过 80 个字符时截断并标记。
  - 不统计 NULL 比例，不给数值范围。
- 取值样例文件记录：规则版本、来源 SQLite 文件的 sha256、库标识、每列的取值方式（全部 / 样例 / 隐私不提供）和取值。它和其他知识准备产物一样放在 Git 忽略的目录里，因为里面是数据集的原始数据。
- 构建 Corpus 时可选地读入取值样例文件，它作为一种新的来源角色进入 Corpus 身份，所以 `corpus_id` 随之改变。列 Chunk 在"取值解释"后面新增一行：全部取值时写明个数和全部值，样例时写明是样例。隐私列和没有取值文件时都不加这一行。新增的行用新的渲染版本标记；不给取值文件、语义配置也没有新字段时，渲染版本和输出都与今天相同。
- 隐私名单首版：student_club 是 `member.first_name`、`member.last_name`、`member.email`、`member.phone`；toxicology 没有。

### 数据约定与语义配置

- 语义配置新增两项，都是可选的：每个库的隐私列名单；每张表的数据约定文本，带来源标记 `observed`，与文件原有的 `inferred` 来源分开记录。旧格式的配置文件照常可用。
- Claude 对两个库的每张表做同一组只读检查，结果写成数据约定的草稿。检查项包括：成对列是否对称存储、是否有只取一个值的列、ID 的组成规律等。草稿交给用户审阅，批准后写进语义配置。没有发现约定的表不写。
- 表 Chunk 在"记录粒度"后面新增一行"数据约定"，只在有约定时出现；metadata 记录它的来源为 `observed`。

### Schema 渲染

- 查询模块的渲染按标签白名单拆行，所以要加上新的两个标签：列的取值和表的数据约定。
- 命中的列在说明后面带上取值；表带上数据约定。没被命中的列仍然只出现在字段目录里。`columns` 和 `ddl` 两种结构写法都一样处理。
- 渲染版本从 `r5-schema-v2` 升一版，记进报告。旧 Corpus 的 Chunk 没有新行，渲染结果与升版前相同。

### Corpus 与存储

- 两份新 Corpus（每库一份）照现有流程完成构建、校验、导入、读回核对，然后用当前的 Embedding Profile 计算向量。导入进现有知识库的现有表，不迁移，不新建角色。旧 Corpus 的行不动。
- 检索按 Knowledge Scope 过滤，新旧 Corpus 不会互相混入候选。BM25 的统计量覆盖整个索引，新 Corpus 进来以后旧 Corpus 的分数会轻微变化，这一点已被接受，报告里注明。
- 用新 Corpus 的目录重新生成一份检索题集（现有的 `eval retrieval-cases --corpus-dir`，题号、Relevant Set 不变，只有 Scope 不同），题集留在本地，manifest 提交。旧题集不动。

### 实验

每次付费运行前都先征得用户同意：

1. 离线重算 R5 八次运行（不付费）。
2. 构建并导入新 Corpus，计算向量（向量计算付费，量很小）。
3. 检索评测：新题集，hybrid + 重排和 lexical 各一次，`top_k=20`、线程数与 R5 之前的检索运行相同。对比对象是干净索引上的旧结果，导入新 Corpus 引起的分数变化在报告中注明。
4. SQL 评测：新 Corpus 上的 ③ 全量知识和 ⑤ 检索 hybrid + 重排，都用 `columns` 写法。题集、模型、提示词、执行上限、4 个线程、`top_k=10` 都与 R5 相同，各跑一次，与 R5 的 ③⑤ 对比。旧 Corpus 不重跑。
5. 结论两个口径并列；逐题分析只看 72 道非冻结题；写明同一配置重跑的波动没有测过；不根据结果调整取值上限、样例个数、渲染规则或提示词。

### 分工

全部由 Claude 用 TDD 实现。用户审阅三样东西：内容匹配的"算对 / 不算对"测试例子、隐私列名单、数据约定草稿。

## 测试决定

- 只测外部行为：给定输入，看输出和记录，不测内部的映射搜索方式或中间结构。规则用固定的小例子覆盖，不用真实模型。
- **内容匹配函数**（新接口）：四条规则各自的正例；明确不算的反例（四舍五入、比例换算、行数不同、少了一行、多出一行内容不同的行、拼接用了别的分隔符）；空结果；"严格匹配则内容匹配"。这组例子交给用户审阅。
- **图评测**（现有接口，参考现有的图评测测试）：用固定的假生成器跑一次评测，检查逐题记录同时有 `execution_match` 和 `content_match`，汇总和 `tables_complete` 拆分里两个口径都在，`export-public` 带上新字段。
- **知识构建**（现有接口，参考现有的知识构建和渲染测试）：取值这一步用一个小的测试 SQLite 库，覆盖全部取值 / 样例 / 键列 / 截断 / 隐私列跳过；构建这一步检查列 Chunk 的取值行、表 Chunk 的数据约定行、`corpus_id` 改变，以及不给新输入时与今天的输出完全相同。
- **Schema 渲染**（现有接口，参考现有的渲染测试）：命中的列带取值，表带数据约定，没被命中的列只有列名，旧格式的 Chunk 渲染结果不变。
- 每张工单提交前跑模块边界测试和全部单元测试；涉及存储的改动跑集成测试。

## 不在范围内

- 值检索（按问题里的词在列值里模糊查找候选值）和 Agent 探查（结果为空或不合理时回头查数据）。
- 修改提示词，或修改 BIRD 原有的字段说明。
- 为内容匹配加更多规则（取整、比例换算、金标准形状不同等）。
- 同一配置重跑的波动测量、旧 Corpus 的重跑、`ddl` 写法以及 ①② 和 lexical 的 SQL 组。
- 知识粒度（知识结构评测是下一项）、token 预算、`top_k` 调整。
- 把金标准有问题的题从计分中剔除或改标签。
- 新的知识库、迁移或数据库角色。

## 补充说明

- 内容匹配的规则是看过 72 道非冻结题的失败之后定的，对全部 88 题（包括 16 道冻结题）统一适用。冻结题不做失败分析，也不做金标准标注（ADR 0001）。
- 离线试算（不调用模型）：仅"列投影 + 去重"两条，就让 R5 每组非冻结题多算对 6–10 道；取整没有任何作用。数字字符串和拼接列预计还能再救回 226、227、255 和 1334、1410、1457、1460 这类题。
- 取值上限 20 是看过两个库各列的取值个数之后定的，没有参照具体的题目。它会让 `expense_description`（12 个值）被全部列出。
- 失败分析文件（`artifacts/analysis/r5-13-wrong-cases.md`）里说"16 道格式题见 SQL 评测文档"，但文档里并没有逐题列出。离线重算时把形式不同的题号补进 SQL 评测文档。
