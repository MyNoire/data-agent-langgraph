# R4b 重排（Reranker）

Status: ready-for-agent

## 问题

R4 的三种检索方法里 hybrid 最好，但 88 题中 Table Complete Recall@5 只有 68.2%，@10 为 85.2%，20 个 Hit 内拿不全的只有 2 道。也就是说，大约 26 道题的相关表已经在前 20 个 Hit 里，只是没排进前 5。BM25、向量和 RRF 都是分别给查询和 Chunk 打分，没有哪一步把"这个问题"和"这个 Chunk"放在一起看。

用户（项目开发者，也是学习者）想知道：**加一步精排，能把已经找到的相关表提到前面吗？代价是多少？** 现在检索里没有重排这一步，无法回答。

## 解决方案

1. 检索请求增加一个独立开关 `rerank`，默认关闭，和 `method` 互不影响。开启后：先按所选方法取前 20 个候选，把问题和每个候选的 `content` 一起交给 Reranker 模型打分，按分数重新排序，再截到 `top_k`。
2. Reranker 用硅基流动的 `Qwen/Qwen3-Reranker-8B`，通过它的 `/rerank` 接口调用，配置和 Embedding 分开。
3. 检索评测增加 `--rerank`。在同一份 88 题、同一份 Corpus 上跑两组：**hybrid + 重排**（主实验，和 2026-11-10 的 hybrid 运行对比）和 **lexical + 重排**（消融：有了重排，还需不需要向量这一路）。逐题分析只看非冻结题。

## 实现决定

### Reranker

- 一个小接口，放在 retrieval 模块（它不读写知识存储，和 Embedder 不同）：
  - `profile_id`：这套重排配置的身份（Rerank Profile）；
  - `rerank(query, documents)`：按输入顺序返回每个文档的相关性分数，条数与输入相同。
- 真实实现调用硅基流动的 `POST {base_url}/rerank`，请求带 `model`、`query`、`documents`（字符串列表），不要求返回文档原文；响应的 `results` 里每项有 `index` 和 `relevance_score`。OpenAI 的 SDK 没有封装重排接口，用 SDK 客户端的通用 `post` 向 `/rerank` 发请求，其余写法和 Embedding 客户端相同（同样的鉴权、60 秒超时、测试时可注入 HTTP 传输），不新增运行时依赖。
- 重试用 SDK 的默认行为，不另写：连接失败、超时、限流和服务端错误自动重试 2 次，仍失败才算重排失败。
- 配置为 `QUERYPILOT_RERANK_BASE_URL`、`QUERYPILOT_RERANK_MODEL`、`QUERYPILOT_RERANK_API_KEY`，与 Embedding 和对话模型分开。
- 真实客户端检查：返回的条数与文档数相同，`index` 恰好覆盖每个文档一次，分数是有限数。不满足、请求失败或超时，都当作重排失败。
- 重排失败统一为 `rerank_error`，错误消息是固定的安全文本，不含查询、Chunk 正文和密钥；底层原因通过异常链保留。
- **Rerank Profile 的身份**是一个可读的字符串：`siliconflow:<模型>:content-v1:<指令版本>`。
  - `content-v1`：候选原样取 Chunk 的 `content`；查询用原文。
  - 指令版本：接口使用 `instruction` 时为 `task-instruct-v1`，传的是 Embedding 查询指令的同一句话（代码里只保留一份）；接口不使用时为 `no-instruct`，不传该参数。
- **指令是否生效要先验证**：用自编的一个问题和几段文本（不取自评测题）各调用几次，带指令和不带指令。带指令被拒绝，或分数与不带指令没有差别（差异不超过两次不带指令调用之间的抖动），就按 `no-instruct` 实现。验证结果记在工单里。

### 检索

- `RetrievalRequest` 增加 `rerank: bool`，默认 `False`。`rerank` 为真且 `top_k` 大于 20 时，请求构造失败（输入校验错误）。
- `retrieve_knowledge` 增加可选参数 `reranker`：开启重排而没有传入时，按配置创建真实 Reranker；不开重排时不创建也不调用。批量调用方应创建一个并传入。
- 开启重排时的流程：
  1. 按 `method` 取候选，数量固定为 20，与 `request.top_k` 无关（hybrid 仍是两路各 50 个候选融合后取前 20）；
  2. 没有候选时直接返回 `no_match`；
  3. 把查询原文和各候选的 `content` 交给 Reranker；
  4. 每个候选的 `score` 换成相关性分数，按分数从高到低稳定排序（同分保持重排前的顺序）；
  5. 截到 `top_k`，重新从 1 编 `rank`。
- 调用 Reranker 发生在只读会话关闭之后：候选行已经取出，不需要让数据库事务等外部服务。
- 查询词检查、Embedding 相关的错误都发生在重排之前，行为和不开重排时相同。重排失败报 `rerank_error`，不退回未重排的结果。
- 候选数 20 是固定常量，不调整。
- `RetrievalResult` 增加 `rerank_profile_id`（请求没有开启重排时为空），结果版本号升级。这两项表示请求按哪套配置执行：开启了重排但没有候选、没有调用 Reranker 时也照常写明，这样一次评测运行里所有题的配置一致。开启重排的结果，配置版本为"方法的版本 + 重排的版本"，例如 `r4-hybrid-v1+r4b-rerank-v1`；`r4b-rerank-v1` 的含义（前 20 个候选、按 Rerank Profile 打分、同分保持原序）写在版本常量旁。
- `RetrievalHit` 结构不变，不保留重排前的分数和名次；`score` 的说明里补上重排后的含义。`elapsed_ms` 包含重排的耗时。

### 评测

- `evaluate_retrieval` 和 `eval retrieval` 增加 `rerank` / `--rerank`，默认关闭，可与 `--method` 组合。默认检索器在一次运行里只创建一个 Reranker，所有题共用。
- 运行配置记录是否重排；报告的 `config.retrieval` 增加结果实际用到的 Rerank Profile。指标、K、`top_k=20` 都不变。评测的 `top_k` 等于候选数，所以重排只改变这 20 个 Hit 的顺序。
- 跑两组：`--method hybrid --rerank` 和 `--method lexical --rerank`。hybrid 不重跑，基线用 2026-11-10 的运行。逐题对比由临时脚本读取 `result.json` 完成，结果写进工单和检索评测文档，不新增对比命令。
- 结果的说法固定为：整体指标 + 非冻结题里"救回 / 弄丢"的题数，并写明 ±1–2 道题属于噪声范围。

## 测试决定

- 好的测试只看对外行为：返回了哪些 Hit、按什么顺序、分数是什么、报什么错误类别、外部服务被调用了几次。不看内部调用了哪些函数。重排的效果由评测回答，不由测试回答。
- 测试用**假 Reranker**：按手写的"文本 → 分数"字典打分，记录被调用的次数和收到的文档，profile id 为 `fake-rerank:test-v1`，不联网。另有一个调用即抛重排错误的版本。
- **Seam 1：`retrieve_knowledge`，真实 PG 加原创小 Corpus**。沿用现有检索集成测试的夹具和假 Embedder，需要 `--require-postgres`。覆盖：
  - 重排后 Hit 按假 Reranker 的分数排序，`score` 是相关性分数，`rank` 从 1 连续；
  - 同分的 Hit 保持重排前的顺序；
  - Reranker 收到的是查询原文和各候选的 `content`；
  - `top_k` 小于候选数时，先对全部候选重排再截断（排在候选后段的 Chunk 可以被提到前面）；
  - 三种 `method` 都能和 `rerank` 组合；
  - 结果里的 `rerank_profile_id` 和配置版本，不开重排时为空且版本不变；
  - 重排失败报 `rerank_error`，不返回未重排的 Hit；
  - 没有候选时返回 `no_match`，Reranker 没被调用；
  - 查询没有有效词时报 `input_error`，Reranker 没被调用；
  - 不开重排时既不调用也不创建 Reranker；没传 Reranker 时按配置创建。
- **Seam 2：`RetrievalRequest`**，单元测试，沿用现有请求校验测试。覆盖：`rerank` 默认关闭；开启重排时 `top_k` 为 20 可以、21 被拒绝；不开重排时 `top_k` 上限仍是 50。
- **Seam 3：真实 Reranker 客户端**，用假的 HTTP 传输代替网络（做法同 Embedding 客户端的测试）。覆盖：请求的地址、模型、查询、文档和指令；分数按 `index` 还原成输入顺序；HTTP 错误、条数不对、`index` 重复或越界、超时都报重排错误；临时的服务端错误会重试，重试后成功就正常返回；错误消息里没有密钥；Profile 字符串。
- **Seam 4：评测运行器**，沿用现有的假检索器测试。覆盖：`rerank` 传进每个检索请求，并写进运行配置和报告。
- 模块边界测试继续守住 retrieval 只依赖 knowledge 和 runtime。

## 不在范围内

- 查询改写、英文词干化、值层面的知识、外键扩展、限制每张表的 Chunk 数、切块粒度和 small-to-big。
- 比较不同的 Reranker 模型、不同的指令写法、不同的候选数；调整 RRF。
- 记录 token 用量和费用；新增对比命令；MRR 和 nDCG。
- 修改 `rerank` 或 `method` 的默认值，以及把检索接入查询图（R5）。Reranker 失败时要不要降级，留给 R5 的查询图决定。
- 自己写重试逻辑、调整重试次数和超时：只用 SDK 默认的重试。SDK 重试用尽后报 `rerank_error`，评测中途遇到会中止整批；评测从断点续跑不做。
- 给单条检索的 CLI 加 `--rerank`：这个命令只有参数解析，没有接到 `retrieve_knowledge`。

## 补充说明

- 真实调用 Reranker 会产生费用（很小）。指令验证和两组评测（每组 88 次调用，每次最多 20 个候选）都要用户明确同意后才运行，运行时记录配置和产物位置。hybrid + 重排还会调用 88 次 Embedding 服务。
- toxicology 整个 Corpus 只有 20 个 Chunk，向量那一路会把它们全部返回，所以 hybrid + 重排在这个库上等于重排整个 Corpus，第一阶段检索不起作用；student_club 有 64 个 Chunk，仍是两阶段。报告里要写明这一点。
- 重排只改变候选的顺序。候选里没有的表（数据值类问题、桥接表）它提不上来，"20 个 Hit 内拿不全"的题数不会因重排而减少。
- 基线 hybrid 运行和新运行各自嵌入查询，查询向量有约 0.001 的余弦抖动，两次的候选可能略有出入；对比时写明。
- 冻结题和开发题一起计分，但逐题分析只看非冻结题（ADR 0001）。候选数、指令和模型都不参考任何题目确定，也不根据评测结果调整。
- GitHub 流程：每完成一张工单，经用户确认后推送 `r4b-reranker`。第一张工单完成后开 Draft PR，正文用 `/pr` 写。
