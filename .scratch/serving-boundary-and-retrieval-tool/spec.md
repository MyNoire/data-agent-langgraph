# 服务边界与检索 tool

Status: ready-for-agent

## 问题

知识结构已经定下（列级 Chunk + hybrid + 重排、`top_k=10`、不展开），但还不能作为可靠的 tool 交给面向业务用户的查询 Agent：

- **没有 Active Corpus**：一个库该检索哪份 Corpus，只能从评测题集或手写文件得到。
- **管理面没有隔开**：检索导入 knowledge 的总入口，用的存储配置带着三个角色的连接串。HTTP `POST /databases` 没有鉴权就能登记数据库，而 CLI 还没有登记命令。
- **预期内的失败没有全部归类**：缺 Embedding / Rerank 配置、查询超长时抛 `ValidationError`，缺 Knowledge Scope、缺表块时是裸 `KeyError`。
- **知识会静默过期**：查询时不比对业务库结构和 Corpus 的 Schema Version。
- **“没找到”在 hybrid 下基本不成立**：实测无关查询在 lexical 下是 `no_match`，在 hybrid 下返回 10 个 Hit，因为向量检索总有最近邻。
- **框架会把服务端错误说成模型的错**：tool 内部的 `ValidationError` 会被 LangGraph 转成“请修正参数再试”。缺 API key 时，模型会反复改写一个本来正确的查询，真正的故障也被藏起来。

## 解决方案

建立服务面：知识管理员在一份配置里指定各库的 Active Corpus；用户端只用 reader 配置，启动时读入这份配置并核对 Schema Version；确定性的检索包成一个薄 tool。模型只给查询文本，得到 Retrieval Context，或者一个带类别、写明是否值得改写重试的失败。

本功能交付五项任务：

1. Active Corpus 配置与读取。
2. 只读配置与导入边界。
3. 登记数据库从 HTTP 移到管理员 CLI。
4. 启动时核对 Schema Version。
5. 检索 tool。

本功能**不把 tool 接进查询图，也不改 `ask`**（默认仍是 `schema` 来源）。两者随下一项功能“模型自主检索”交付：那项功能比较固定检索与自主检索之后，`ask` 就切到胜出的知识库方案。所以启动核对和知识过期的效果在本功能里只能从 tool 观察到；现有入口唯一可见的变化是登记从 HTTP 移到 CLI。

## 实现决定

### 职责

- **knowledge**：提供结构版本的公开计算和只读配置类型；构建、导入、校验仍是管理面能力。
- **retrieval**：仍是确定性服务，不知道自己被模型调用；只依赖只读配置，并向上提供结构核对。
- **querying**：提供用户端启动（读 Active Corpus、逐库核对）和检索 tool 这个薄适配层。业务库位置由它向 databases 取得，再交给 retrieval 核对；不新增 retrieval → databases 的依赖，它自己也继续不导入 knowledge。
- **entrypoints**：管理员登记命令只在 CLI。

### Active Corpus

- 配置名为 `config/active_corpus.json`，内容是 `database_id → corpus_id + schema_version`。
- 初始值如下。它们抄自 values 检索题集的 manifest，之后两者不再关联：

| database_id | corpus_id | schema_version |
|---|---|---|
| toxicology | `50c156f8700b7312ea4391384c2a4f7cc64e750e6457edd7815463e08560a768` | `45b2e99ae191cbcde4fa377e702dcd498c98abaf0f7193565861601d653ba799` |
| student_club | `748167d2fce64e4575d9de96495a4ed0ac1b8c2bbdd1b3dd07f873751b3092b7` | `20441054b528d9e52458069d101e8290f2698b873886d66f2e7a9a52803fe6c1` |

- 用户端启动时读一次，不热加载。
- 文件缺失、不可读或不符合格式时，启动以 `configuration_error` 失败。

### 启动核对

对配置里的每个库，用与构建相同的算法重算 Schema Version：

| 情况 | 结果 |
|---|---|
| 一致 | 可用 |
| 不一致 | 只停用这个库，`knowledge_stale` |
| 未登记、文件不可用、提取失败（包括含有视图） | 只停用这个库，`database_unavailable` |

不在配置里的库不参与核对；对它调用 tool 时返回 `scope_not_configured`。

### 只读配置与导入边界

- 只读配置类型只含 reader 连接串和读取所需的超时。打开只读会话和检索只依赖它；管理面现有配置继续可用。
- 不做“发现 admin 连接串就拒绝启动”：开发机的同一份环境文件里有三个角色的连接串。
- retrieval 从 knowledge 只能按名字导入读取相关的能力：读会话、Knowledge Scope、只读配置、Embedder、相关错误与类型、结构核对所需的函数。整模块导入也算违规。
- 用户入口（HTTP 和 `query` 命令）不得导入 knowledge 或 evaluation。

### 登记数据库

- 删除 HTTP `POST /databases`，新增 `querypilot data register`，沿用登记的全部检查。其他 HTTP 接口不变。

### 检索 tool 的契约

- **模型可见的输入只有 `query`**。`database_id` 来自运行状态，Knowledge Scope 来自运行时 context。
- **固定配置**：hybrid + 重排、`top_k=10`、三种知识类型、不展开，都不出现在参数 schema 里。
- **成功**：返回渲染后的 Retrieval Context、命中的表名，以及“候选不保证足以回答”的固定说明。组装和渲染复用现有逻辑，知识文本与检索来源逐字相同。不设分数阈值，够不够、是否拒答由 Agent 决定。
- **失败**：在返回给模型的文本里写明类别、安全的固定原因和是否值得改写重试。类别必须在文本里，因为转换成 OpenAI 格式的 tool 消息时不带框架的 status 字段。

| 情况 | 类别 | 改写重试 |
|---|---|---|
| 空查询、超长、没有有效词 | `input_error` | 是 |
| 没有候选 | `no_match` | 是 |
| 缺配置、缺依赖 | `configuration_error` | 否 |
| 库没有 Active Corpus | `scope_not_configured` | 否 |
| 启动核对未通过 | `knowledge_stale` / `database_unavailable` | 否 |
| Embedding、重排、读取层失败 | 沿用已有类别 | 否 |
| 命中的表缺表块 | `knowledge_state_error` | 否 |

- **谁归类**：在产生错误的层完成，tool 只做转换。
- **三种错误分开处理**：
  - 模型传参的结构错误（缺字段、类型错）沿用 LangGraph 默认提示，包括字段原因和对参数的回显，不自定义。
  - 预期内的失败按上表返回。
  - 其他都是程序错误，照常抛出。tool 内部意外的 `ValidationError` 不能被框架当成传参错误吞掉。
- **消息内容**：tool 自己生成的失败消息不含查询原文、SQL 和连接串。这条不约束框架的参数错误提示：它回显的是模型自己刚生成的参数。
- **不回退，不自己重试**（SDK 自带的重试除外）。
- **返回内容是数据**，不是指令或授权依据。
- **追踪**：tool 不经过查询图使用时也关闭 LangSmith 上传。

### 分工

- **用户写（乒乓 TDD，Claude 先写失败的测试）**：tool 的参数、运行状态与 context 的注入、成功与失败到返回值的映射。
- **Claude 写**：只读配置、边界测试、Active Corpus 读取、结构核对、检索层错误归类、CLI 登记、文档。

## 测试决定

### 什么是好测试

只测调用方看得到的行为，不断言内部函数的调用顺序和私有结构。单元测试用临时 SQLite、临时配置文件和假的外部依赖，不联网、不调用付费服务；模型和检索的质量由评测回答，不在这里测。

### 测试接口（seam）

共三组，只有第一组是新接口。

**1. 检索 tool 的一次调用（主接口，新增）**

测试按用户端的方式启动，再模拟模型发起一次 tool 调用，只断言参数 schema 和模型收到的内容。LangGraph 的 `ToolNode` 只在测试里充当调用方。只读配置、Active Corpus 读取和启动核对都经这里测，不另设接口。

- 成功：参数 schema 只有 `query`；伪造的库、Knowledge Scope、top_k 和运行时都不生效；知识文本与检索来源逐字相同；表名和固定说明都在。
- 启动：一致时可用；给一个库加列后它返回 `knowledge_stale`，另一个库照常；只改数据仍可用；未登记、提取失败、含视图返回 `database_unavailable`；配置文件缺失或损坏时启动失败。
- 失败：契约表里每种情况至少一个用例，断言类别、是否重试，以及自己生成的消息不含敏感内容。联网之前就会失败的情况（输入错误、缺配置）走真实检索代码，不用假检索器代替。
- 程序错误：包括 tool 内部意外的 `ValidationError`，都会抛到调用方。
- 追踪：环境变量打开追踪时，单独使用 tool 也不会上传。
- 集成：在专用测试库上只给 reader 连接串，用假 Embedder 和假 Reranker 走同一接口检索成功。

不测试框架参数错误提示的具体文案。

**2. 架构边界扫描（沿用）**

- 合成源码里，retrieval 导入管理操作、整模块导入 knowledge、用户入口导入 knowledge 或 evaluation，都会被报告。
- 现有生产源码通过。

**3. HTTP 与 CLI 入口（沿用）**

- CLI 登记后，HTTP 能列出这个库并读到它的结构。
- 非法登记仍被拒绝。
- `POST /databases` 不再可用。

### 已有先例

- 检索来源查询图的测试：假检索器、假表块读取、运行时 context，以及逐字断言 Retrieval Context。
- 关闭追踪的测试：打开环境变量后断言追踪仍是关的。
- 模块边界测试：合成项目加真实源码扫描。
- HTTP 接口测试、CLI 契约测试，以及知识检索在专用测试库上的集成测试。

### 何时运行

每张工单提交前跑架构测试和全部单元测试；涉及只读配置或只读会话的工单另跑集成测试。`ask` 与查询图的现有测试必须保持通过。

## 不在范围内

- 模型自主检索：接进查询图、检索循环、调用次数上限、与固定流程的对比实验、切换 `ask`。
- 优化参数错误提示：在“模型自主检索”里看真实调用轨迹，模型确实常传错、改不对时再做。
- 总时限、降级、连接池、把部署检查移到启动时：主功能全部完成后逐步优化。
- Access Grant、选库、列级权限。`POST /queries` 继续接受任意只读 SQL，能读到隐私列，留给以后的 Access Grant。
- 分数阈值与拒答。
- 知识内容修改、重建 Corpus、正文脱敏。
- 热切换、灰度、MCP、辅助开发者建库的 Agent。
- SQL 修复、记忆。

## 补充说明

- **依据**：ADR 0004（管理面与服务面分离）；术语以术语表为准。
- **测试接口合并的代价**：主接口失败时定位稍慢，而且拆工单时要先打通一条最小的 tool 成功路径，启动核对和错误归类才有地方观察。
- **已做的可行性验证（2026-11-22，均未调用付费服务）**：
  - 两个正式库重算的 Schema Version 与上表一致；临时副本删一行版本不变，加一列版本改变。
  - 在 LangGraph 1.2.12 上用离线探针验证：参数 schema 可以只有 `query`，伪造的范围参数不生效；保留默认参数错误提示时，仍能返回自己的失败类别，并让程序错误抛出。探针不是产品测试，实现时仍按 TDD 补测。
- **已知限制**：启动核对发现不了运行中的改表，也发现不了只改数据造成的取值样例过期；只读配置类型和静态导入检查不是进程级隔离，部署时只下发 reader 凭据仍然必要。
- **下一步**：用户运行 `/to-tickets` 拆工单。
