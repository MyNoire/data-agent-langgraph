# 检索评测并发（eval retrieval --workers）

Status: ready-for-agent

## 问题

检索评测一题一题串行跑。R4b 的 hybrid + 重排在 88 题上用了 18.9 分钟（单题 P50 10.6 秒），时间几乎都花在等 Embedding 和 Reranker 服务返回，本地计分可以忽略。用户因此不愿意把 R4b 合并回 `master`：每做一次对比实验都要等十几分钟。

用户（项目开发者，也是学习者）还想借这件事学并发编程：此前基本没用过 `threading` 和 `concurrent.futures`。

## 解决方案

1. `eval retrieval` 增加 `--workers N`，默认 1。大于 1 时用线程池同时检索多道题。
2. 工作线程只做"调一次检索器"；计分、逐题记录和进度事件都留在主线程，线程之间不共享可变状态。
3. 报告内容和串行时一致（题目顺序、指标都不变），只是每题的耗时会受并发影响，所以把 `workers` 记进运行配置和报告，并规定耗时只在 `workers=1` 的运行之间比较。
4. 某道题遇到致命错误或用户按 Ctrl+C 时，不再开始新题，正在请求中的题跑完后整批失败。

## 实现决定

### 接口

- `evaluate_retrieval` 增加关键字参数 `workers`，默认 1；`eval retrieval` 增加 `--workers N`，默认 1。
- 不为 `workers` 单独写校验：小于 1 时线程池自己会报错。
- 运行配置（`retrieval_run_config`）和报告的 `config` 都增加 `workers`。报告版本号不变。
- 默认检索器不变：一次运行仍然只创建一个 Embedder 和一个 Reranker，所有线程共用；每次检索自己开一个知识库只读连接。

### 并发模型

- 用标准库的线程池，线程数为 `workers`。`workers=1` 也走线程池，不保留单独的串行循环。
- 工作线程处理一道题时只做一件事：调一次检索器，返回检索结果，或返回"这题是 `input_error`"。它不计分、不写事件、不碰任何列表。
- 主线程按**完成顺序**逐个取回结果，每取到一个就写一条 `eval_case_finished` 事件。事件里 `case_index` 仍是这题在题集里的位置，新增 `completed_cases`（已完成几题，从 1 递增）。
- 每个结果放回它所属题目的位置。全部完成后，主线程按**题集顺序**计分、组装 `records` 和 `config.retrieval`，所以报告不随完成顺序变化。
- 每题的 `elapsed_ms` 仍取检索结果自己测的值。

### 停止

- 一个停止标志（`threading.Event`），整次运行共用：
  - 工作线程在开始每道题之前检查它，已置位就跳过这题，不调检索器；
  - 工作线程遇到致命错误（`input_error` 以外的任何异常）时，先置位，再把异常抛出；
  - 主线程因任何原因离开收集循环时置位，包括收到工作线程的异常和用户按 Ctrl+C。
- 由此得到的保证：某题失败后，同一线程不会再开始新题；其他线程最多把手上正在请求的那一题跑完。`workers=1` 时就是"失败之后一次都不再调用"。
- 在途的题跑完后结果丢弃。主线程抛出它最先看到的那个错误（原始异常，不包装），运行记为 failed，不写 `result.json`，错误类别的取法和现在相同。
- `input_error` 不置位：这题按空的 Hit 列表计分，其他题继续。
- 退出前要等在途的请求结束。客户端超时是 60 秒，加上 SDK 重试，最坏情况下 Ctrl+C 之后还要等几分钟。

### 限流与重试

- 不写限流器，不写自己的重试，仍只用 SDK 的默认重试。
- 依据：一次重排请求最多 20 个候选，约 2,000–3,000 Token（按字符数估算）；整份 88 题约 26 万 Token、176 次请求，低于用户账号每分钟的限额（RPM 2,000，TPM 1,000,000）。

### 文档

- 检索评测文档补上 `--workers` 的用法、耗时的比较规则，以及验收运行的结果。
- 术语表不加词，不写 ADR。

### 分工

乒乓 TDD。用户写 `evaluate_retrieval` 里的并发主体（提交任务、按完成顺序收集、停止标志）；Claude 一次写一个失败的测试并说明它验证什么，每个测试之前先用几行小例子讲一个概念。`--workers` 参数、配置记录和文档由 Claude 直接完成。

## 测试决定

- 好的测试只看对外行为：检索器被调用了哪几题、报告里的顺序和内容、事件的顺序和字段、抛出什么错误、运行记录的状态。不看用了线程池的哪个方法。
- 并发行为用线程同步工具确定地构造，不用 `sleep` 计时：
  - "确实同时在跑"：假检索器里放一个需要 N 个线程同时到达才放行的关卡（`threading.Barrier`），串行实现会在关卡上超时而失败；
  - "完成顺序"：假检索器按题目等待各自的 `threading.Event`，由测试决定谁先完成。
- **Seam 1：`evaluate_retrieval` 加假检索器**，沿用现有检索评测运行器的测试文件和夹具，不连 PG、不联网。覆盖：
  - `workers=N` 时 N 道题同时处于检索中；
  - 后提交的题先完成时，`records` 仍按题集顺序；
  - 事件按完成顺序写出，`completed_cases` 从 1 递增，`case_index` 是题集位置；
  - 并发时 `input_error` 只记在那一题上，其他题照常完成；
  - 致命错误：`workers=1` 时只调用 1 次（现有测试保持不变）；`workers>1` 时在途的题跑完，排队的题不被调用，抛出的是原始错误，运行记为 failed，没有 `result.json`；
  - 主线程中途失败时，排队的题不再被调用（Ctrl+C 走的是同一条路径，不单独模拟键盘中断）；
  - `workers` 写进运行配置和报告的 `config`，默认是 1。
- **Seam 2：CLI `eval retrieval`**，沿用现有的 CLI 测试。覆盖：`--workers` 传到运行器并写进运行配置。
- 多个线程共用一个 OpenAI 客户端是否安全，不由单元测试回答，由验收运行检验。

## 不在范围内

- SQL 评测（direct / graph）的并发。
- 断点续跑：等看到并发后的真实总时长再决定。它需要运行中逐题落盘，和"失败不写结果"有冲突，要单独对齐。
- 限流器、自己写的重试、调整重试次数和 60 秒超时。
- `asyncio`、多进程、连接池。
- 记录总时长或 Token 用量的新字段；修改任何指标或题集。
- 修改 `rerank` / `method` 的默认值。

## 补充说明

- **验收**：实现完成后跑一次 `--method hybrid --rerank --workers 8`，同样的 88 题和 Corpus。看总时长（对比串行的 18.9 分钟）和召回指标（对比 R4b 的 hybrid + 重排运行，±1–2 道题属于噪声）。运行收费，要用户明确同意后才跑，并记录配置和产物位置。不为了对比重跑串行。
- 能快多少取决于服务端。R4b 的结果里，同样 50 道题在两个时段的耗时中位数是 1.0 秒和 11.3 秒，服务本身波动很大；8 个线程未必快 8 倍，一次运行的总时长只能说明量级。
- 并发运行里的单题耗时包含服务端同时处理多个请求的影响，所以耗时 P50 / P95 只在 `workers=1` 的运行之间比较；已有报告都是 `workers=1`。
- 冻结题照常一起计分；这次不看任何题的结果来改检索（ADR 0001）。
- GitHub 流程：在 `r4b-reranker` 分支上继续，每完成一张工单经用户确认后推送；PR #2 的正文扩成"R4b + 评测并发"，用 `/pr` 更新。
