# 04: 审查后的返工：改成主线程派发

**What to build:** 评测开发者在评测中途出错或按 Ctrl+C 时，可以确定不会再有新题开始、不会再多花钱；默认的 `--workers 1` 下进度事件始终按题集顺序。做法是把"一次全部提交 + 停止标志"换成"主线程派发"：同时在途的题不超过 `workers` 个，处理完一道才提交下一道。

**Blocked by:** 01, 02, 03

**Status:** ready-for-human

规格：`.scratch/eval-concurrency/spec.md` 的"并发模型"和"停止"两节（2026-11-12 审查后修订）。背景见工单 01 Comments 里的审查记录。结对工单：用户写 `evaluate_retrieval` 里的并发主体，Claude 写测试并审查。

- [ ] 只有主线程提交任务，同时在途的题不超过 `workers` 个；处理完一道完成的题（计分、记录、写事件）才提交下一道
- [ ] 不再有停止标志和"跳过"的题；工作线程的函数只返回检索结果或"这题是 `input_error`"
- [ ] 一批同时完成的结果里有致命错误时，这一轮不再提交新题
- [ ] 计分在主线程拿到结果时就做；`records` 和 `config.retrieval` 仍按题集顺序
- [ ] 测试"主线程失败后没有新题开始"通过，且不依赖时间（现在是红的）
- [ ] 测试"`workers=1`、400 道题、检索瞬间返回时事件按题集顺序"通过（现在是红的）
- [ ] 测试"`workers=2` 时致命错误之后没提交的题不被调用，在途的题跑完"通过
- [ ] 其余检索评测运行器的测试保持通过
- [ ] 用 lexical 各跑一次 `--workers 1` 和 `--workers 8`（不调用收费服务），逐题结果除 `elapsed_ms` 外完全相同
- [ ] 检索评测文档和 `evaluate_retrieval` 的 docstring 里"已知问题"的两处改回成立的说法
- [x] `eval retrieval --workers` 小于 1 或不是整数时按参数错误退出，不建运行记录（Claude，343d056）

## Comments

- 测试（2026-11-12，Claude）：停止行为的三个测试换成了确定的版本，另加一个事件顺序的测试。
  - "主线程失败后没有新题开始"：主线程在写第 1 题的完成事件时出错，并在出错的那一刻放行还在检索中的第 2 题。主线程派发下，主线程进入这一步之后就不会再提交，所以第 2 题什么时候完成都不影响结果，不需要靠时间。
  - "致命错误之后没提交的题不被调用"：在途的第 2 题要等"运行第 1 题的那个工作线程退出"才返回，而线程池只在关闭时才让空闲线程退出，所以它一定在评测停止提交之后才完成。这个测试依赖标准库线程池"空闲线程在关闭时退出"的行为。
  - 这些测试在仓库的临时副本里对两种实现各跑过：对主线程派发的写法，23 个测试连跑 5 次全部通过；对现在的实现，恰好是上面标"现在是红的"两个失败（连跑 3 次）。
- 约定的一个顺序：主线程对一道完成的题先计分、记录、写事件，然后才提交下一道。测试"主线程失败后没有新题开始"是在写事件这一步让主线程出错的，所以它也钉住了这个顺序。
