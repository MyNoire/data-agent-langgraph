# 02: 进度与中断：按完成顺序写事件，主线程退出时停止

**What to build:** 评测开发者在并发运行时，每道题完成的那一刻就看到一条进度事件，某一题很慢也不会让进度停住；事件里能看出已经完成了几题。按 Ctrl+C 或主线程中途出错时，程序不再开始新题，等在途的请求结束后退出。

**Blocked by:** 01

**Status:** ready-for-human

规格：`.scratch/eval-concurrency/spec.md`。结对工单（乒乓 TDD）：分工同工单 01，这次的概念是 `as_completed` 和并发里的 `try / finally`。本工单不做真实运行。

- [x] `eval_case_finished` 按完成顺序写出：后提交的题先完成时，它的事件先出现（测试用 `threading.Event` 决定谁先完成，不用 `sleep`）
- [x] 事件新增 `completed_cases`，从 1 递增到题目总数；`case_index` 仍是这题在题集里的位置
- [x] 报告的 `records` 和 `config.retrieval` 仍按题集顺序（工单 01 的测试保持通过）
- [x] 主线程因任何原因离开收集循环时置停止标志：主线程中途失败时，排队的题不再被调用
- [x] Ctrl+C 走同一条置位路径，不单独模拟键盘中断
- [x] 多道在途的题都失败时，抛出主线程最先看到的那个错误（没有单独的测试，见下）
- [x] 事件里仍然没有问题原文

## Comments

- 实现（2026-11-12）：和工单 01 一起由用户写完，经过见工单 01 的 Comments。收集结果用 `as_completed`，每个结果放回它所属题目的位置，线程池结束后按题集顺序计分和组装报告；`try / finally` 写在线程池的 `with` 块里面，保证在线程池退出、开始等排队任务之前就置位。
- 测试"报告保持题集顺序、事件按完成顺序"是确定的：测试把一个进度流接到运行上，第 1 题要等这个流收到第 2 题的完成事件才返回，所以第 2 题一定先完成、先被主线程处理。
- **偏离规格的一处**：测试"主线程失败后排队的题不再开始"依赖时间。主线程出错时第 2 题可能已经在检索中，测试没有办法知道停止标志是哪一刻置位的，所以让第 2 题之后的检索各停留最多 0.5 秒，给主线程留出置位的时间。规格要求并发测试不靠计时；这一项没有确定的测法，取舍是"有一个留足余量的测试"好过"没有测试"。它失败的条件是主线程执行一条 `finally` 用了 0.5 秒以上。用户知情。
- 没有单独测试的两项：
  - 多道在途的题都失败时抛哪一个：由 `as_completed` 的顺序决定，是"主线程最先取到的那个"。两个都失败时哪个先被取到取决于线程调度，没有确定的断言可写。
  - 真实的 Ctrl+C：没有模拟键盘中断。Claude 另外用一个独立脚本（不在仓库里）模拟了主线程等在 `as_completed` 里时收到中断：在 Windows 上，主线程要到下一个任务完成时才收到 `KeyboardInterrupt`，之后还要等在途的请求结束。也就是说按下 Ctrl+C 后的等待时间比规格写的多一层：先等到下一道题完成，再等其余在途的题。
- 测试结果：见工单 01。
- 审查（2026-11-12）：结果记在工单 01 的 Comments 里；其中两条实质问题（主线程退出时停止标志置得太晚、已完成的 Future 顺序不定）都落在本工单的范围内，等用户决定怎么改。
