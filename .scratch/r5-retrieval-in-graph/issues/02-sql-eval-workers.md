# 02: SQL 评测并发

**What to build:** 评测开发者用 `eval graph --workers N` 同时跑多道题，报告内容和顺序与逐题运行相同，八次运行能在二十分钟左右跑完。

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

沿用检索评测的主线程派发结构。

- [x] `eval graph --workers N`，默认 1
- [x] 工作线程里跑一道题的图和金标准 SQL；结果比对、逐题记录和进度事件都在主线程
- [x] 同时在跑的题不超过 N 道，主线程处理完一道才提交下一道
- [x] 单题的错误和现在一样记为 error 并继续；主线程自己出错或被中断时不再开始新题
- [x] 报告的逐题记录按题集顺序排列，与哪题先跑完无关；`workers` 为 1 和大于 1 时，除耗时外报告相同
- [x] 运行配置和报告记录线程数
- [x] 确认编译好的图、运行上下文和日志中间件可以被多个线程同时使用；不行的部分改成每个线程各用一份，结论记在 Comments
- [x] 测试用假 SQL 生成器，覆盖：报告顺序、`workers` 为 1 和 4 时结果相同、单题出错后继续、主线程出错后不再开始新题
- [x] SQL 评测文档写明：`workers` 大于 1 时逐题耗时只在相同线程数的运行之间比较

## Comments

- 实现（2026-11-14，Claude）：`run_graph(..., workers=N)` 和 `eval graph --workers N`。结构和检索评测相同：主线程是唯一提交任务的地方，同时在跑的题不超过 N 道，处理完一道（比对、记录、写完成事件）才提交下一道。工作线程里的 `_run_case` 只跑查询图和金标准 SQL，把原始结果和题内的异常放进返回值，不抛出。
- 多线程共用的结论：
  - 编译好的查询图：可以共用（没有 checkpointer，每次 `stream` 的状态相互独立）。
  - 日志中间件 `GraphLogMiddleware`：可以共用，它按框架的调用 UUID 分开记账，并且已经有锁。
  - 运行上下文：**有一处不行，已修**。SQL 审计日志是第一次执行 SQL 时才创建的，文件用排他方式新建；几个线程同时第一次执行 SQL 时都去创建，后到的报 `FileExistsError`。第一个并发测试（3 道题在关卡上同时放行）稳定复现了它：3 题里 2 题记成 error。修法是给创建加锁，在 runtime 模块里，不在评测里绕。
- 耗时改为在工作线程里量（从这道题开始跑到金标准 SQL 执行完），不含它在主线程里排队等处理的时间。
- 事件：`eval_case_started` 在主线程提交这道题时写，`eval_case_finished` 按完成顺序写，`completed_cases` 是已完成题数，`case_index` 是题集里的位置。`workers=1` 时和以前一样是题集顺序，原有的事件关联测试不用改。
- 测试（`tests/test_graph_eval.py`，新增 9 个）：同时在图里、报告顺序与完成顺序、并发时单题出错不影响别的题、主线程出错后不再开新题、`workers` 1 和 4 报告相同、线程数进运行配置和报告、命令行参数、非正整数被拒。用两种故意改坏验证过：一有题完成就先提交下一道 → "主线程出错"测试失败；记录按完成顺序放 → 三个测试失败。
- 真实数据验证（不调用模型）：用金标准 SQL 充当生成器，在 88 题上跑 `workers=1` 和 `workers=8`，都是 88/88，除耗时外逐题记录相同；运行目录 `artifacts/runs/evaluation/2026-11-13/` 下 `6b18ff1e836b4755816bdfc35bd2d36b`（1 个线程）和 `e439648868c6473f93854327925218ce`（8 个线程）。
- 没验证：真实模型在 8 个并发下会不会被限流，留到工单 07 第一次真实运行时看。
