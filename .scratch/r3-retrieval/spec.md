# R3：把一次检索收进 retrieve_knowledge

Status: ready-for-agent

## 问题

用户（项目开发者）想把检索接进查询图，但现在没有"做一次检索"的完整操作。完成一次检索需要调用方自己串起 5 个文件里的私有函数：准备查询词、打开只读会话、BM25 搜索、按 ID 回读、组装 Hit（实现中已合并为一次搜索，见"检索内部流程"）。最容易出错的就是这一串调用，偏偏它一个测试也没有。17 个集成测试已经写好了期望的入口 `retrieve_knowledge`，因为函数不存在，它们全部失败。

另外，检索链路防御过度：

- 一个错误要被改名三次才到调用方。
- 同样的资源上限写了两处。
- 同一个风险被检查好几遍。
- 10 个数据模型里有 4 个没人使用。

读这段代码的人和 AI 都要花力气分辨哪些检查真正起作用。

## 解决方案

检索只提供一个入口：给定一个检索请求（查询文本、Knowledge Scope、top_k、要找的知识类型），在指定的 Corpus 中做 BM25 关键词检索，返回按相关性排好序的 Hit 列表。失败时只抛一种检索错误，并带上错误类别。

去掉重复的错误层、限额副本、多余校验和未使用的模型。检索模块内部只分四块：公开入口、数据模型、查询词准备、搜索 SQL。

## 用户故事

1. 作为查询图的开发者，我想调用一个函数就完成一次检索，这样新增检索节点时不用了解检索内部的步骤。
2. 作为查询图的开发者，我想让检索结果明确区分"找到了"(matched)和"没找到"(no_match)，这样图可以按结果走不同分支。
3. 作为查询图的开发者，我想让"查询里没有任何有效词"报输入错误，而不是当成没找到。这样像"请问的谢谢"这种问题不会被静默放过。
4. 作为查询图的开发者，我想让检索失败时只收到一种错误类型，并通过类别区分原因，这样只需要捕获一种异常。
5. 作为查询图的开发者，我想通过错误类别区分"输入有问题""范围不存在或不匹配""知识库连不上或超时""超出资源上限"，这样能决定重试、澄清还是放弃。
6. 作为查询图的开发者，我想让每个 Hit 带上 rank 和原始 BM25 分数，这样以后做融合或重排时有依据。
7. 作为查询图的开发者，我想让每个 Hit 带上原始标题、正文和表列定位，这样能直接拼进 Retrieval Context。
8. 作为查询图的开发者，我想让 Hit 的排序稳定：分数从高到低，同分时按 chunk_key、再按 chunk_id 排序，这样同样的输入每次结果一致，评测可以复现。
9. 作为查询图的开发者，我想让检索严格限制在请求给定的 Knowledge Scope 内，这样不会读到别的 Corpus、别的库或别的 Schema Version。
10. 作为查询图的开发者，我想按知识类型（table / column / relationship）过滤，这样可以只查列或只查关系。
11. 作为查询图的开发者，我想让查询词之间是"或"的关系，即任意一个有效词命中就算候选，这样查询里夹杂的无关词不会把有用的结果挡掉。
12. 作为查询图的开发者，我想让中文查询按分词后的词项匹配，不退回到子串匹配，这样匹配行为可以预测。
13. 作为查询图的开发者，我想让 top_k 只截取最终排序后的前 K 条，这样不会出现先截断再过滤导致结果变少的问题。
14. 作为查询图的开发者，我想让结果附带查询文本的 sha256 和检索配置版本，这样日志和评测能对上号，又不用记录问题原文。
15. 作为查询图的开发者，我想让结果附带本次检索的耗时，这样能观察检索的性能。
16. 作为评测开发者，我想让检索返回的分数和次序与直接调用 pg_search 插件的结果完全一致，这样可以确认没有隐藏的人工加分。
17. 作为评测开发者，我想用同一个入口对不同 Knowledge Scope（不同 Build Profile 构建出的 Corpus）做检索，这样能比较不同的知识结构方案。
18. 作为维护者，我想让检索的错误只在入口处转换一次，这样排查错误来源时只需要看一个地方。
19. 作为维护者，我想让资源上限只定义一次，这样修改时只改一处就生效。
20. 作为维护者，我想删掉没人填写或从未被创建的模型，这样读代码时不用猜它们的用途。
21. 作为维护者，我想删掉只做格式转换的包装函数，这样检索流程能在一个地方从头读到尾。
22. 作为维护者，我想让测试只通过公开入口验证行为，这样调整内部实现时不用跟着改测试。
23. 作为学习者（用户本人），我想亲手写出检索主流程的串联逻辑，这样能讲清楚一次检索的状态是怎么变化的，以及每一步的取舍。

## 实现决定

**公开接口**
- 检索模块对外只暴露 `retrieve_knowledge(request, settings) -> RetrievalResult`，再加上请求、结果、Hit 和错误这几个类型。`settings` 是知识存储的读取配置。
- 这一轮不加 `run_context`、运行事件或 CLI 命令。

**结果形状**
- RetrievalResult 包含：结果版本、请求 ID、matched / no_match、Knowledge Scope（只在顶层出现一次）、检索方法、检索配置版本 `r3-bm25-v1`、规范化版本、查询 sha256、top_k、知识类型、命中数、Hit 列表、耗时。
- Hit 固定 11 个字段：rank、score、chunk_id、chunk_key、knowledge_type、title、content、content_hash、schema_name、table_name、column_name。不返回 Scope、文档引用、关系引用、SourceRef 和 metadata。
- 关系类 Hit 的三个表列定位保持原来的空值；表类 Hit 的 column_name 为空。这一条依据 2026-11-02 已定的"检索范围收敛"。

**错误**
- 调用方只会收到 `KnowledgeRetrievalError` 这一种错误，它带有错误类别。
- 错误类别直接沿用知识读取层已有的类别，检索层只额外加 `input_error`，不另外复制一份类别表或提示文案。
- 读取层的错误只在 `retrieve_knowledge` 里转换一次，原始异常通过 cause 保留。
- 删除从未被创建的 `RetrievalError` 模型。

**资源上限**
- 三个上限（范围内最多 5000 个 Chunk、检索文本 8 MiB、结果 1 MiB）只在知识读取层的限额对象里定义。
- 检索配置对象只记录分词和停用词的版本与摘要。
- 结果大小交给读取时已有的字节检查。top_k 最大为 50，所以不再在序列化时另做检查。

**删除的重复校验**
- 检索配置对象里拿常量和常量比较的校验器。
- 结果对象上逐条检查 rank、Scope、类型和重复的整体校验器。
- 结果里对知识类型的二次去重。
- 搜索函数里"请求 Scope 是否等于会话 Scope"的检查。会话就是用这个 Scope 打开的，两者必然相等。
- 每个 Hit 重新计算正文 hash 的校验。导入时的回读核对已经覆盖了这个风险，而检索账号只有读权限。这一条推翻了 2026-11-02"保留原正文校验"的决定。
- 只保留检索请求上对用户输入的校验：查询文本非空、不含 NUL、长度上限；top_k 在 1 到 50 之间；知识类型合法且不重复。

**删除的模型和包装**
- 删除 SemanticProfileRef、ProvenanceRef、SourceRef 和 RetrievalExecutionProfile。
- 删除检索层的只读会话包装函数，它只做了限额拷贝和错误改名。
- 删除检索层重复的文本校验函数。

**检索内部流程（结对核心）**
- 准备查询词：现有的中英文片段切分、jieba 搜索模式分词、表达词过滤和保序去重保持不变。过滤后没有任何有效词时报 `input_error`。
- 在只读会话内执行**一条** BM25 搜索 SQL，直接返回排好序的行。每行包含 9 个原字段和插件分数；Scope 显式绑定，不关联查询父文档。
- 按返回顺序组装 Hit：rank 从 1 开始连续编号，score 用插件的原始分数。
- 有 Hit 时为 matched，否则为 no_match。
- 修订（2026-11-02，同日）：原计划分两步，先搜索 ID，再按 ID 读回字段。去掉父文档关联之后，第二步只是从同一张表再取一次字段，所以合并为一条 SQL。原来"两步结果要不要对账"的问题因此不存在了。以后做混合检索时，如果候选多、正文大，需要"融合后再按 ID 取正文"，届时再拆。

**搜索 SQL**
- BM25 的查询 SQL 留在检索模块内，与检索的其他步骤放在一起。
- 可检索字段在索引定义和查询 SQL 里各写一份，两者是否一致由真实 PG 集成测试保证，不另加同步机制。

**分工**
- 机械部分由 Claude 完成：上面的删除、合并，模型精简，以及测试适配。
- `retrieve_knowledge` 主体的串联逻辑由用户亲手写，Claude 负责审查。

## 测试决定

- **好测试的标准**：只通过公开入口观察行为，即输入一个检索请求，检查结果或错误类别。不调用私有函数，不检查中间状态。内部重构时测试不需要修改。
- **主要测试接口**：`retrieve_knowledge`，跑在真实 PostgreSQL 测试库上（库名必须是 `querypilot_knowledge_test`），使用原创的小型夹具 Corpus。现有 17 个失败的集成测试就是 TDD 的"红"，涵盖：
  - 中英文匹配、部分命中、无匹配；
  - 无有效词时报 `input_error`；
  - Hit 的原字段、rank 连续性和稳定排序；
  - 分数和次序与直接调用插件完全一致。
  - 这些测试按 11 个字段适配：删掉对 Scope、文档引用、关系引用和 source_ref 的断言；关系类 Hit 改为断言三个定位字段为空。
- **保留的内部测试**：查询词准备的测试保留。它是纯函数，中文分词边界情况多，全部改用 PG 测试太慢。
- **范围和故障相关的集成测试**（范围不存在、范围不匹配、坏状态、容量超限）：改为通过 `retrieve_knowledge` 触发，断言错误类别。
- **删除的测试**：私有函数的练习文件和教程练习、单元测试里直接测内部函数或断言"入口不存在"的部分、只验证已删除模型的测试。
- **可参照的已有测试**：现有知识存储集成测试里的专用测试库夹具和只读会话测试；`tests/integration/_bm25_fixtures.py` 里的原创夹具。

## 不在范围内

- `run_context`、检索运行记录和进度事件。
- `retrieval search` CLI 命令。
- 检索评测（Recall@K、样例集、评测运行器）。
- SourceRef 和详细来源投影（结构定位、语义来源、修正记录、关系出处）。
- Hit 展开为 Document、Retrieval Context 的组装。
- 把检索接入查询图、修改 SQL 生成器的接口。
- 统一索引定义和查询 SQL 的字段来源。
- 向量检索与混合检索。
