# 知识结构评测：Small-to-Big

Status: ready-for-agent

## 问题

知识侧马上要冻结，之后的工作都在 Agent 一侧（检索做成工具、修复、选库与拒答、多轮）。冻结前还剩一个问题：知识按什么粒度交给模型。用户（项目开发者，也是学习者）原本打算比较列级、表级和 small-to-big，并在相同的 token 预算下评测。对齐时发现这个设计在当前的两个库上不成立：

- **表级比不出东西。** student_club 只有 8 张表，toxicology 只有 4 张。表级 Chunk 按 `top_k=10` 取会取回整个库，结果等于全量知识 ③。这已经测过（非冻结内容匹配 54/72），和检索 ⑤ 相同。要比出差别，只能硬定一个很小的 `top_k`，而这个数字没有依据。参考项目 vanna 的旧版也是表级知识：DDL 和每表一段说明，各取 10 条，再加 14k token 上限。它面向几百张表的数仓，所以 10 张不算多。
- **token 预算同样是人为制造的压力。** 两个库的全量知识只有约 1.8k 和 4.9k 提示词 token，任何合理的预算都放得下。

真正值得回答、两个小库也能回答的问题只剩一个：**被命中的表，要不要带上全部列的说明和取值**，而不只是命中的那几列。现在的检索上下文已经是"列块命中 → 带上整张表的表块（用途、粒度、全部列名、主外键）"，没命中的列只出现列名。

## 解决方案

新增 **Small-to-Big** 开关：检索仍按 Chunk 匹配，选出的表不变，但每张被命中的表以完整的 Document 交给 SQL 生成，内容与全量知识里这张表逐字相同。然后在 88 题上跑一组 SQL 评测，与已有的 ⑤（列级）和 ③（全量）比较内容匹配和提示词 token，按事先定好的规则选出冻结时用的粒度。

预期是打平，然后保持列级。离线分析（只看非冻结题）显示：表拿全、但有普通列没被命中的 14 题里，⑤ 错了 6 题，而 ③ 已经带着这些列的全部说明，在这 6 题上仍错了 5 题。实测用来确认或推翻这个预期。

## 实现决定

### 查询图

- `build_query_graph` 新增编译参数 `small_to_big: bool`，默认 `False`。只对 `retrieval` 来源生效。在其他来源上传 `True` 时，编译时报 `ValueError`。
- 打开时，`retrieve` 节点照常检索一次，按 Hit 第一次出现的顺序得到命中的表。然后用已有的全量读取函数（`knowledge` 来源用的那个，可注入）读出当前 Scope 的全部 Chunk，只保留属于命中表的 Chunk（表、列、关系都按 `hit_table` 归属）。表 Chunk 取自其中的表 Chunk，不再单独按表名读。
- 组装：命中表的全部 Chunk 按全量读取时的顺序组装，因此每张表内部的列和关系顺序与 ③ 相同。再按检索得到的表顺序重排各表。这一步放在查询模块的上下文组装里，是一个纯函数，由图的测试覆盖，不单独公开。
- 渲染沿用 `render_context`，规则不变，`SCHEMA_RENDER_VERSION` 不升。展开后每张表的渲染与 `knowledge` 来源里这张表逐字相同。
- 允许查询的对象范围不变，仍是这个库的全部用户表。`tables_complete` 仍按 Hit 所属的表计算，与开关无关。
- 关闭时，节点和组装路径与今天完全相同。`GRAPH_VERSION` 不升，开关作为独立字段记录；旧运行没有这个字段，视为关闭。
- `ask` 和 HTTP 入口不暴露这个开关。

### 图评测

- `eval graph` 新增 `--small-to-big / --no-small-to-big`，默认关闭。打开时 `--context-source` 必须是 `retrieval`，否则在写任何运行记录之前报错。
- 开关写进运行配置：要登记进运行配置的字段白名单，否则会被悄悄丢掉。报告新增 `small_to_big` 字段，`export-public` 的白名单同步加上。
- 报告结构的其他部分不变。按库统计的提示词 token 平均值、最小值和最大值，在结果分析时由逐题记录里已有的 `prompt_tokens` 算出，不写进报告。
- 不新增逐题字段。对齐时提过"每题记进上下文的表数"，最后没有做：⑤ 不重跑，没有这个字段可比；small-to-big 和 ⑤ 的表按构造相同（都是 Hit 所属的表），③ 是全部表，这个数没有新的信息。

### 实验

只有一次付费运行，运行前先征得用户同意：

- **新运行 small-to-big**：`eval graph --context-source retrieval --small-to-big`，hybrid + 重排、`top_k=10`、`columns` 写法、检索题集 `retrieval_cases_values`（values Corpus 的 Scope）、88 题 SQL 题集、模型 `gpt-6.1-sol`、提示词 `direct-v2`、`QUERYPILOT_MAX_ROWS=10000`、`QUERYPILOT_QUERY_TIMEOUT_MS=20000`、4 个线程。
- **复用的对照组**：⑤ 检索列级 `14d32c18`、③ 全量知识 `50e2edf1`，都在 2026-11-21 跑在同一份 values Corpus 上。知识库此后没有导入新 Corpus，BM25 统计量不变。
- **判定规则**（看结果前定下）：按非冻结 72 题的内容匹配，small-to-big 与 ⑤ 相差不超过 3 题算打平；打平时选提示词 token 更少的那组。只有 small-to-big 比 ⑤ 多对 4 题及以上，才改用 small-to-big。检索指标和严格执行匹配只用来解释，不参与判定。
- **报告内容**：三组的内容匹配和严格执行匹配（整体、非冻结、分库）；按库的提示词 token 平均值、最小值和最大值；`tables_complete` 拆分；small-to-big 相对 ⑤ 在非冻结题上的翻转题号。写进 SQL 评测文档。逐题分析只看非冻结题。注明同一配置重跑的波动没有测过。
- 不根据结果调整 `top_k`、渲染规则、提示词或知识内容。

## 测试决定

- 只测外部行为：编译图、注入假的检索函数、假的全量读取函数和假的生成器，看生成器收到的 Schema 文本和评测记录。不测组装函数的内部结构。用固定的小例子，不用真实模型和真实检索。
- **查询图**（现有接口，参考现有的检索来源图测试和知识来源图测试）：
  - 假检索命中两张表的部分列，比如 `member.position` 和 `event.event_name`。打开开关后，Schema 只含这两张表，每张表的渲染与 `knowledge` 来源对同一份 Chunk 渲染出的对应表逐字相同，表的先后按检索名次。
  - 只命中某张表的关系 Hit，也会展开这张表。
  - 关闭开关时，输出与今天逐字相同。
  - 在 `schema`、`ddl`、`knowledge` 来源上打开开关，编译时报 `ValueError`。
  - `ddl` 写法下，展开的表同样使用建表语句。
- **图评测**（现有接口，参考现有的检索来源图评测测试）：用假生成器跑一次 `--small-to-big`，运行配置、报告和 `export-public` 里都有 `small_to_big: true`；不带 `--small-to-big` 时报告里为 `false`；在非检索来源上使用时，开始前报错且不留下运行记录。
- 每张工单提交前跑模块边界测试和全部单元测试（`--ignore=tests/integration`）；不涉及存储改动，集成测试不是必须的。

## 不在范围内

- 表级 Chunk（新 Build Profile）、表级检索和它的 `top_k` 选择：推迟到加入大库之后。
- token 预算和超出预算时的截断规则。
- 入向关系、外键扩展（R6）、补桥接表。
- 改进 Document 内容：列说明仍是 BIRD 英文原文；隐私列没有取值；没有业务口径。
- 重跑 ③ ⑤、测量同一配置重跑的波动、lexical 组、`ddl` 写法的 SQL 组。
- 改提示词、`top_k`、检索方法或重排配置。
- 在 `ask` / HTTP 入口暴露开关，或改变查询图的默认行为。

## 补充说明

- 离线分析用的是 2026-11-21 hybrid + 重排检索运行（`12228012`）和 ⑤ ③ 的逐题结果，只对非冻结题逐题查看，冻结题只计数。非冻结 72 题里，表没拿全的 4 题、表和列都命中的 35 题、表拿全但缺列的 33 题。缺的大多是主键或外键，它们已经出现在字段目录和主外键行里；缺普通列的 14 题中 ⑤ 错了 6 题（1338、1376、1404、1422、197、201，其中 197 是已标注过金标准有问题的题），③ 在这 6 题上错了 5 题。
- 以 `member` 表为例（命中 `position`、`email`）：列级渲染 490 字符，small-to-big 渲染 1,658 字符。
- 如果结论是改用 small-to-big，或结果与预期明显不同，再考虑是否写 ADR；保持列级则不需要。
- 对齐时参考了 vanna 的源码（本地 `vanna-main` 2.0.2）：旧版是表级 DDL 和说明，加问答 SQL 示例，纯向量各取 10 条，再加 14k token 上限；新版不再固定检索 schema，改为 Agent 自己跑 SQL 查库，再加上保存成功做法的记忆。后者对应路线图后面的"模型自主检索"和长期记忆。
